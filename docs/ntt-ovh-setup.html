simpl-ovh-mcp on the NTT OVHcloud account

Step-by-step configuration manual. Version 1.0, 19 September 2026. For the operator of the server. Contains no credentials.

What this manual gets you. The same MCP server that deployed Simpl-Open on the personal OVH project, pointed at the NTT OVHcloud account instead, verified end to end, and ready either to inspect the cluster NTT already runs or to create a fresh Simpl-Open deployment in the NTT project. Estimated time: 45 minutes of clicking, most of it on the OVH side, plus 50 minutes if you deploy a new platform.

1. One design decision first: a second server, not a re-pointed one

The OVH credentials are global to a server instance; deployment profiles are per cluster, but they all use the same OVH identity. So the clean way to work with two OVH accounts is two Railway services from the same repository, each with its own variables, its own bearer token and its own volume. Recommended layout:

Railway serviceOVH accountPurpose
ovh-mcp (existing)personal, project simpl-open-bridgeKeep until the personal project is emptied, then delete.
ovh-mcp-ntt (new)NTTThe one you will use from Monday.

If you would rather re-point the existing service, only steps 3.4 and 4 change: replace the three OVH variables and redeploy. Profiles of the personal cluster stay on the volume and become useless, which is harmless.

2. On OVHcloud, NTT account

2.1 Find the project id

  1. Log into www.ovh.com/manager with the NTT account.
  2. Public Cloud, select the project, then Settings in the left menu. Copy the Project ID.
  3. Keep it as OVH_CLOUD_PROJECT.

2.2 Create an OAuth2 service account

  1. Top right, your name, Identity and access management (IAM), tab Service accounts (in some regions labelled "OAuth2 clients").
  2. Create a service account. Name it simpl-ovh-mcp-ntt, description "MCP server for Simpl-Open deployment", flow Client credentials.
  3. OVH shows the client id (looks like EU.xxxxxxxxxxxxxxxx) and the client secret exactly once. Keep both in your password manager. Never paste them anywhere except Railway.
  4. Note the service account's identity URN, shown on its detail page. It has the form urn:v1:eu:identity:credential:<account>/oauth2-EU.xxxxxxxx. You need it for the policy.

2.3 Create the IAM policy

The service account has no rights until a policy grants them. Two resources, two action families, nothing else.

  1. IAM, tab Policies, Create a policy.
  2. Name: simpl-ovh-mcp-ntt.
  3. Identities: choose the tab for service accounts and add simpl-ovh-mcp-ntt. (The screen opens on local users and user groups; the service account is under its own tab.)
  4. Resources: add the Public Cloud project and the DNS zone. If the zone is not offered in the picker, create the policy with the project only and add the zone afterwards.
  5. Actions: "all actions" on the selected resources is acceptable for a deployment tool. If you prefer an explicit list, use the two wildcards below.

Equivalent API call, if you prefer the console at api.ovh.com/console with POST /iam/policy:

{
  "name": "simpl-ovh-mcp-ntt",
  "identities": ["urn:v1:eu:identity:credential:<account>/oauth2-EU.xxxxxxxx"],
  "resources": [
    { "urn": "urn:v1:eu:resource:publicCloudProject:<project-id>" },
    { "urn": "urn:v1:eu:resource:dnsZone:sc3poc.xyz" }
  ],
  "permissions": { "allow": [
    { "action": "publicCloudProject:apiovh:*" },
    { "action": "dnsZone:apiovh:*" }
  ] }
}
Check the zone URN type before posting. A zone can be exposed as dnsZone or domain. GET /iam/resource lists the exact URNs the account has. A wrong type is accepted silently and every DNS call then fails with 403.

The policy deliberately excludes the account itself (urn:v1:eu:resource:account:...). The server's ovh_whoami tolerates the resulting 403 on /me; nothing else needs it.

2.4 Choose the DNS suffix

Every Simpl-Open host name is <service>.<agent>.<suffix>, served by one wildcard record. Pick a suffix that does not collide with NTT's existing records, for example mcp.sc3poc.xyz, giving authority.fe.authority01.mcp.sc3poc.xyz. The server creates the wildcard itself in step 6.

3. On Railway

3.1 Create the service

  1. In the Railway project, New, GitHub repo, select the server repository. Name the service ovh-mcp-ntt.
  2. Builder is taken from railway.toml (DOCKERFILE). Do not switch to Railpack; it would build a server without Helm.

3.2 Attach the volume

  1. Service, Volumes, Add volume, mount path /data.
  2. The image's entrypoint takes ownership of the mount at start, so the root-owned mount is not a problem. Profiles, kubeconfigs and the audit log live here and survive redeploys.

3.3 Public domain

  1. Service, Settings, Networking, Generate domain.
  2. Target port 8080. This is the port the container listens on; a different value gives a permanent 502.
  3. Note the domain, for example ovh-mcp-ntt-production.up.railway.app.

3.4 Variables

Generate the bearer token on your machine first:

Do not set SIMPL_MCP_TRANSPORT. The server detects Railway's PORT and serves HTTP. A copied stdio value produces a server that starts cleanly, listens on nothing and answers 502. Also do not set PORT; Railway injects it. FASTMCP_CHECK_FOR_UPDATES=off is already baked into the image.
  1. Save the variables. Railway redeploys.
  2. Open the deploy log. The healthy first lines name the transport http, the mode, and the state directory as writable.

4. Connect a client

Claude.ai connector: Settings, Connectors, Add custom connector. URL https://<railway-domain>/mcp. Authentication: bearer token, paste the token. The server answers the connector's handshake without OAuth.

Claude Code:

claude mcp add --transport http simpl-ovh-ntt https://<railway-domain>/mcp \
  --header "Authorization: Bearer <token>"

From a shell, using the repository's driver script, which reads the token from ~/.simpl-mcp-token:

SIMPL_MCP_URL=https://<railway-domain>/mcp \
  .venv/bin/python scripts/mcp-call.py ovh_whoami '{}'

5. Verify, in this order

#CheckExpected
1curl https://<domain>/healthz200 without a token. Anything else: the service is not up or the port is wrong.
2mcp_infomode: operate, state_dir_writable: true, ovh.auth_mode: oauth2, 70+ tools registered.
3ovh_whoamiThe NTT account. A 403 on /me alone is fine and reported as such.
4ovh_projects_listExactly the NTT project(s) the policy allows. If empty: the policy's resource URN is wrong.
5ovh_dns_zonesThe NTT zone. If empty: the zone URN type (section 2.3).
6ovh_kube_listNTT's existing cluster simpl-managed-cluster (Kubernetes 1.35, region GRA9) appears. Nothing was changed by this.
7ovh_registry_listEmpty, or an existing registry if NTT has one.
All seven green means the server is correctly wired to the NTT account. Everything from here on is a deployment choice.

6. Two ways to use it on the NTT account

6.A Inspect the cluster NTT already runs

NTT deploys with Jenkins and Terraform: cluster simpl-managed-cluster, charts 3.1.x, issuers named dev-prod and dev-selfsigned, OpenBao engine dev-int, domain sc3poc.xyz. The server can attach to it read-only without touching it.

  1. simpl_profile_create(name="ntt-managed", kube_id="<id from ovh_kube_list>", domain_suffix="sc3poc.xyz", dns_zone="sc3poc.xyz", make_active=true)
  2. ovh_kubeconfig_fetch(). Credentials are stored on the volume; only the API server URL is returned.
  3. simpl_status(), k8s_pod_health(namespace=...), simpl_diagnose(), argocd_apps().
Limit. The install and initialise tools assume the issuer and OpenBao names this server creates. On the NTT cluster use the inspection tools (status, diagnose, logs, events, ArgoCD read) and avoid simpl_install_*, simpl_setup_issuers and argocd_app_sync until the profile carries NTT's names. Syncing the common application on a live platform rotates its Kafka and Redis passwords.

6.B Create a fresh Simpl-Open deployment in the NTT project

This is the flow that produced the working platform on the personal project. About 50 minutes, nothing shared with the existing NTT cluster.

  1. Plan and profile. simpl_plan(agents=["authority"], sizing="demo", region="GRA11", domain_suffix="mcp.sc3poc.xyz"), then simpl_profile_create(name="ntt-dev", region="GRA11", domain_suffix="mcp.sc3poc.xyz", dns_zone="sc3poc.xyz").
  2. Cluster. ovh_kube_create(name="simpl-ntt-dev", region="GRA11", flavor_name="b3-16", desired_nodes=2). Poll ovh_kube_get until READY (3 to 8 minutes), then ovh_kubeconfig_fetch().
  3. Platform. simpl_bootstrap_platform(). Wait for the load balancer address in simpl_status().
  4. DNS. ovh_dns_ensure_wildcard(zone="sc3poc.xyz", sub_domain="*.mcp", target_ip="<LB address>"), then simpl_verify_dns(deep=true).
  5. Issuers and storage. simpl_setup_issuers(mode="acme", acme_email="<team address>", acme_staging=false). Production ACME, never staging: the platform's own components verify TLS and reject staging certificates. Then simpl_setup_rwx_storage().
  6. Common components. simpl_install_common(resource_preset="low"). Watch with simpl_wait and k8s_pod_health(namespace="common01") until 12 pods are ready, 10 to 20 minutes.
  7. Authority. simpl_install_agent(agent_type="authority"), then simpl_initialize_authority(). 27 pods; trust chain reported VALID by simpl_diagnose().
  8. Registry for the Bridge. Either (a) the GitLab container registry, once an administrator enables it: create a deploy token with read_registry and write it as a pull Secret with k8s_apply of a kubernetes.io/dockerconfigjson Secret named gitlab-registry-pull in authority01; or (b) ovh_registry_create(name="simpl-images", region="GRA"), then ovh_registry_user_create(registry_id=..., namespace="authority01"), which writes the pull Secret itself. Build and push the image as documented in the Bridge repository, documents/IMAGE-DISTRIBUTION.md.
  9. Bridge. bridge_deploy(image_registry="<registry host>", image_tag="1.0.0-INC1-<commit>"), then bridge_status() and bridge_search(...). The proof is degraded: false, not the 200.

Do not park a Simpl-Open cluster. Scaling the nodes to zero and back leaves every database-backed component unable to authenticate, and the cause is not established. Treat the platform as rebuildable: delete it with simpl_teardown(scope="platform") in admin mode with destructive writes enabled, delete the registry with ovh_registry_delete, and rebuild in 50 minutes when it is needed again.

8. Problems seen once, so you do not see them twice

SymptomCause and fix
Every request answers 502; log looks healthySIMPL_MCP_TRANSPORT=stdio copied into the variables, or the domain's target port is not 8080. Remove the variable; set the port.
Errno 13 on /data at startVolume mounted root-owned. Fixed in the image's entrypoint; if seen, the image is stale: redeploy.
ovh_whoami reports 403 on /meExpected with a project-scoped policy. Not a problem.
ovh_projects_list or ovh_dns_zones emptyWrong resource URN in the policy, usually the zone type. Check GET /iam/resource.
x509: certificate signed by unknown authority in openbao-configStaging ACME issuer. Switch to production and delete the stored TLS Secret so it is reissued.
Kafka, Keycloak, users-roles crash-looping after a restartParked cluster, see section 7. Rebuild.
Authentication failures after an ArgoCD sync of the common applicationThe chart mints Kafka and Redis passwords at render time; a sync rotates them. Restart the consumers, or avoid syncing that application.
Bridge pod crash-loops on "Unable to find datasource"Image older than commit 9cbda97. Use a current build.

9. Security notes

  • The bearer token is the only lock on the server. Treat it like the OVH secret. Rotate it by changing the variable; every client must be updated.
  • The server never returns credentials: kubeconfigs, registry passwords and OVH secrets stay on the volume or in the cluster. Tool outputs redact them.
  • Give colleagues a readonly instance if they should look but not act. It is a second Railway service with the same OVH variables and SIMPL_MCP_MODE=readonly.
  • Every write is recorded in the audit log on the volume; mcp_audit reads it.
  • Delete the service account and policy on the personal OVH account once that project is empty.

Naming used above: Railway service ovh-mcp-ntt; OVH service account and policy simpl-ovh-mcp-ntt; profiles ntt-managed (attach) and ntt-dev (fresh); cluster simpl-ntt-dev; suffix mcp.sc3poc.xyz. Change them consistently if NTT has conventions.
